# Conventions

## Source of truth

The spec describes the code on `main` at the commit a chapter names.
Descriptive statements are checked against that implementation revision.
Normative MUST and MUST NOT requirements are authoritative: an
implementation that violates one is defective unless the maintainer
explicitly approves a specification change. Track each disagreement in
an issue, with the implementation evidence and the approved resolution.
Chapters are written by reading the source, the models and the tests,
not from memory of earlier prose.

## Chapter skeleton

Every protocol chapter uses these sections, in this order:

1. **Goal**: what the protocol achieves for whom.
2. **Actors**: the parties and the attacker.
3. **Message flow**: the messages in order, with a diagram.
4. **Normative operations**: the cryptographic steps, with MUST and
   SHOULD, each naming the source file and function.
5. **State machine**: states, transitions, what each side persists.
6. **Failure cases**: every way the protocol stops, and what the user
   is told.
7. **Security considerations**: what holds, what does not, and the
   claims (S-numbers) this chapter backs.
8. **Vectors**: which entries of the vectors file exercise it.

## Requirement words

MUST, MUST NOT, SHOULD and MAY are used as in RFC 2119, and they
define the required behavior. A MUST the code violates is a defect and
gets an issue; changing the requirement requires explicit maintainer
approval, recorded with the specification change.

## Claims

Claims are numbered S1, S2, ... and never renumbered; a withdrawn claim
keeps its number and says it was withdrawn. Each claim carries:

- **Attacker**: who is assumed and what they control.
- **Statement**: one sentence, falsifiable.
- **If false**: what breaks for a user.
- **Status**: *shipped* (code on `main`, proof in CI), *partial* (the
  mechanism exists, the proof or part of the behaviour is missing, and
  the entry says which), or *planned* (a tracked gap, not a claim).
- **Backed by**: the test function, lemma or certification lane, by
  name, and the normative section.

## Versioning

The book is tagged `MAJOR.MINOR[-draft]`. A tag is immutable; a
correction is a new tag. Spec versions are independent of app and Core
versions; the changelog maps each spec tag to the Core commit it was
extracted from. Wire-format changes bump MINOR while the spec is a
draft and MAJOR afterwards.

## Machine-readable artefacts

A machine-readable file (vectors, transcripts, schemas) is added only
together with the check that fails when it and the code disagree.
Today: the vectors are generated by Core's test suite and compared by
CI. Schemas will follow the same rule (ADR-076).

## What holds each statement true

Every kind of statement in this book drifts from the code in its own
way, and each has, or lacks, a check that fails when it does:

| Statement | Held true by | Fails when |
|-----------|--------------|------------|
| A vector value | Core's `protocol_test_vectors_tests.rs` recomputes it from the shipped functions; this book's copy is compared byte for byte in CI (`check:vectors`), as is the docs site's | A derivation changes, or a copy lags Core `main` |
| A wire schema and its examples | Core's `wire_schema_tests.rs` generates both from the `v2` types, proves every published bound by parsing a value at it and one past it, and fails when the committed files differ from what the types generate; this book's `check:wire-schema` compares its copy with Core's and validates every example against the schema | A type or bound changes without regenerating the files; the copy here lags Core; a definition loses its example or an example stops validating |
| A claim's lemma | Core's `test:formal-code` job runs the Kani harnesses and the wipe tests on merge requests that touch the code they check, and `test:formal-models` runs most Tamarin models and the device-link Quint invariants on merge requests that touch the models; both run nightly on `main` and on release tags, and `check:formal-triggers` fails when a harness or model sits outside its job's trigger paths; `test:formal-extended`, nightly (manual on a merge request), runs the `ble_handshake.spthy` lemmas and the Bluetooth and multi-stage Quint machines. Tamarin and Quint checks pair with a control that must fail; the Kani harnesses have none | The lemma stops proving or the control stops failing |
| A test, lemma or function name | `check:claim-names` greps every backticked lower-case name longer than eight characters that the claims chapter and the protocol chapters contain, as a whole word anywhere under Core, the two relays and the end-to-end repository on `main`, so a name found only in a comment passes; a name in an open merge request waits in `ci/claim-names.pending` until it lands (spec!6, vauchi/private#874) | A test, lemma or function is renamed or removed, or a pending name lands and its line stays |
| A claim's proof, as a set | In Core, the tests, lemmas and invariants a claim names carry `@claim: S<n>`, with gaps the claim's entry names, and so do the end-to-end lane cases S1, S3 and S12 name (e2e!288); `check:claim-annotations` fails when a shipped or partial claim has no annotation left in Core or e2e, or an annotation names no claim (spec!13, vauchi/private#874) | The last annotated test behind a claim is deleted, or a claim is removed while tests still cite it |
| Any of the above, between spec edits | The four drift checks (vectors, wire schema, claim names, claim annotations) run on a nightly schedule against the mains (spec!12); Core's `check:spec-names` runs the name and annotation checks against each Core merge request that touches a crate, and warns when the vectors fixture differs from this book's copy (core!2078) | Core moves while nobody edits the spec; a Core MR renames or removes a cited name |
| A behaviour behind a sentence | The `Spec:` trailer (VGT12): a `feat:`, `fix:` or `refactor:` commit on a Core protocol path or a relay's `src/` states `Spec: unchanged` or the claims and sections it moves; VGT12 is a local commit-msg hook only, no CI job checks it (vauchi/private#950); review holds the statement against the diff | A protocol commit carries no statement, or a false one |
| A certification lane | The end-to-end repository's blocking lanes on every merge request, `main` and schedule; the release gate refuses a missing, stale or partial report | A lane case fails or is skipped |
| A normative sentence, state or failure case | The chapter's status line pins the Core commit it was read from; re-extraction is by hand | Core moves past the pinned commit (the changelog records re-extractions) |
| A source-file link | None; links name `main` | A file is moved or renamed |
| A wire format without a schema | The signed OHTTP key record and the escrow messages have none; a schema is added only with the validator that fails on disagreement (ADR-076), as the relay wire's was | Not applicable until one is added |

The current automated comparisons extract artifacts from Core and check
the spec against them. Core does not yet verify conformance against a
pinned spec tag (ADR-076, decision 5). This enforcement gap does not
override normative requirements.

## Scope

The spec covers the personal layer: one person, their devices, their
contacts. Organisation identities are an extension point and are
marked as such where a protocol would have to change.
